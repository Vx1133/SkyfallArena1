# Update #22: Preserve the map, integrate the elements and pillars, unify surfaces, and make pilot control optional

## Implementation notes

- The existing experience, place, lobby, arena grid, tile positions, tile dimensions, and major geometry are retained. This update does not rebuild the map from scratch.
- The server keeps the existing `SkyfallArena/Environment` folders. It refreshes only `ActiveMap/GeneratedDecor`, preserving other hand-authored lobby and map children.
- The destructible tile grid is reused by its existing `Tile_x_z` names. Existing tiles are not repositioned or resized by this update. Missing tiles are created only when absent.
- The existing lobby `WaitingPlatform` is reused. The Cyberpunk arena floor captures its current Color, Material, MaterialVariant, Reflectance, TopSurface, and BottomSurface, then reapplies that profile when tiles reset.
- Solid architectural surfaces in the Cyberpunk map, including the underside, perimeter trim, cross braces, pillar foundations, columns, collars, and caps, now reuse the lobby floor's Material, MaterialVariant, and Reflectance. White, blue, and silver part colors remain intentional art-direction accents. Neon lines remain Neon so they continue to emit light.
- The Cyberpunk sky is now daytime: `ClockTime = 14.2`, a fresh default Roblox `Sky` instance, zero stars, no moon, a pale-blue Atmosphere, restrained sunlight rays, and lower Bloom. Existing Sky instances are removed when the Cyberpunk lighting profile is applied, preventing a previous night skybox from remaining active.
- Four corner pillars are generated by the dedicated `CyberpunkPillarService`. Their foundations overlap the perimeter rails, their foot bridges extend into the rail line, and their mid-height collars meet the existing cross braces. Layered collars, aligned crowns, surface-matched finishes, and narrow cyan light spines make the pillars read as part of the arena structure.
- Existing Fire, Water, Earth, and Air models are discovered by the `SkyfallElement` tag plus the `SkyfallElementType` attribute, by specific `SkyfallFireElement`, `SkyfallWaterElement`, `SkyfallEarthElement`, and `SkyfallAirElement` tags, or by supported names such as `FireElement`, `WaterZone`, `EarthArea`, and `AirElement`.
- The element integration adds three thin, non-collidable visual transition layers around each discovered existing model or BasePart. It does not move, resize, replace, or create the element models themselves. A subtle point-light pulse is limited to one light per discovered element.
- **Asset limitation:** the current GitHub source tree does not contain authored Fire, Water, Earth, or Air models. Those objects must already exist in the published Workspace and be named/tagged as above, otherwise the service warns and does not build their transition layers. Place them under a preserved Workspace folder, not inside `ActiveMap/GeneratedDecor`.
- Human aircraft control requires a player to set `PILOT: ON` while waiting and also press `PLAY`. If no ready player opted in, an eligible bot controls the aircraft. The opt-in is consumed for that round. The existing owner-only Debug Drone override remains a separate explicit opt-in.
- `StreamingEnabled` was already enabled in `default.project.json`; this update preserves the existing mobile-oriented streaming settings.
- Terrain editing and `Lighting.Technology = Future` are intentionally not forced. The current arena floor is a grid of BaseParts, and no device profiling evidence justifies a global Future lighting change.
- A Codex handoff brief is stored at `docs/handoffs/CODEX_UPDATE_022.md`. There is no live Codex session/API connection exposed in this ChatGPT workspace, so the brief is prepared in-repository but has not been submitted to a Codex process.

## Validation

- CI runs the existing Update #19 Lune policy test and the Update #22 pilot opt-in policy test.
- Python structural validation checks the daylight setup, material-profile propagation, and four-pillar assembly.
- Selene linting and Rojo place build remain part of the validation workflow.
- Roblox Studio visual/physics/mobile playtesting is still required for final in-engine confirmation. A successful static build does not prove runtime behavior.
